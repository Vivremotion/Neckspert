# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A fretboard-memory trainer for guitarists, built as a rhythm game. The player hears a metronome, sees a prompt ("F, corde de B"), and plays the note on a real guitar on the beat (mode 1, _locate_), or taps the note name for a given string/fret (mode 2, _identify_). Spaced repetition (FSRS via `ts-fsrs`) decides what comes back; only the first, _cold_ attempt at a card after a delay feeds retention stats. Read `PRODUCT.md` for the product rules and `docs/brief.md` for the original brief. Product docs, plans and UI copy are in French; code, identifiers and comments are in English.

```sh
npm run dev            # vite dev server
npm run build          # static build (adapter-static, SPA fallback index.html)
npm test               # all Vitest projects, single run
npm run test:unit      # Vitest watch mode
npm run check          # svelte-kit sync + svelte-check (types)
npm run lint           # prettier --check

```

Single file / single test:

```sh
npx vitest run src/lib/domain/scoring/judgement.spec.ts
npx vitest run src/lib/domain/scoring/judgement.spec.ts -t "late"
npx vitest run --project client   # only jsdom tests
```

Vitest has two projects (`vite.config.ts`): `*.spec.ts` runs in **node** (`server`), `*.svelte.spec.ts` runs in **jsdom** (`client`). Any test that renders components or uses runes must be named `*.svelte.spec.ts`. `expect.requireAssertions` is on, so every test must assert. Dexie specs import `fake-indexeddb/auto`. The merge gate used throughout the plans is `npm test && npm run check`.

`scripts/functional-ui.mjs` drives real pages in headless Chrome against running dev servers (it fails on behavior errors and on text under 16px). It is not part of `npm test`.

## Architecture

Svelte 5, runes only (forced for all non-`node_modules` files), SvelteKit with `ssr = false`, no component library, native CSS with variables. Layered, ports-and-adapters:

- `src/lib/domain/` — pure logic, no Svelte, no browser APIs. `types.ts` holds the shared domain model (cards keyed by `cardKey(mechanic, itemKey)`, attempts, verdicts, settings, planned items). `exercise/` (the catalog of exercises, `Progression`, `Execution`, `startTempo`/`nextTempo`), `timing/` (time relations: `beatTiming` for mode 1 with the lead-beat ladder, `identifyTiming` for mode 2, and the `Round` state machine that judges one prompt in time), `mechanics/` (`MechanicRules`: id, time relation, item key, judge; `locateRules`, `identifyRules`, the `mechanicRules` registry), `music/` (fretboard, naming, `locateItems`/`practiceCards` over frets 1–11; chords and voicings: `spelling.ts` `SpelledNote`, `chord.ts` degrees and qualities, `voicing.ts` `Voicing` (the degree each string carries) with its stable key and `voicingOccurrences` on the neck, `triads.ts` `closeTriadVoicings`, `candidates.ts` `voicingCandidates`), `scoring/` (verdicts, answer windows, recall threshold, fatigue), `progress/` (FSRS scheduling, temperature cold/hot, `introduction.ts` queue order, `review.ts` cold eligibility, session selectors, stats, neck map, grades).
- `src/lib/application/` — `ports/` defines the interfaces infrastructure must implement (clock, metronome, note detector (`onNote`, and `onRejected` for attacks whose pitch was not confirmed), cues, calibration, repositories, backup). `app.ts` defines `AppServices`, the single object screens consume, provided through Svelte context (`provideAppServices` / `useAppServices`). `session/contract.ts` defines `PlaySessionController` and its reactive `PlayView` — the contract between orchestration and the play screen. `session/SessionController.svelte.ts` implements it (runes-based state machine: count-in → awaiting → verdict…), asking a `SessionSelector` for each prompt; it is built with `(session, prepare, deps)`, where `prepare(sessionId)` returns the selector and the session's executions (one tempo per exercise, frozen at start, `session/executions.ts`). `session/AttemptRecorder.ts` stores attempts (and completes their observations once the span closes), `session/observationSpan.ts` (`ObservationSpan`) collects the observations of one attempt, `session/sensors.ts` turns the detector and the screen into observation sources (`SensorFactory`, `noteSensor`, `tapSensor`). `mechanics/` holds the `MechanicPresenter`s (`locatePresenter`, `identifyPresenter`, `NECK_PRESENTERS`): scene, sensor, prompt, reveal. `services/createAppServices.ts` builds `AppServices` from `SessionDeps`.
- `src/lib/infrastructure/` — adapters. `audio/clock` (one `WebAudioClock` owns the single `AudioContext`; `WebAudioMetronome` schedules beats), `audio/input` (`WebAudioInput`: the one raw input, shared; its frames feed every detector), `audio/detection` (AudioWorklet `frame-processor.ts` → onset detection + pitch via `pitchy` → `NoteTracker`), `audio/chords` (`NnlsChordVerifier` behind `ChordVerifierPort`: verifies a played chord against known candidates by fitting harmonic combs, reports at 250/500/1000/2000 ms after each attack, judge variants side by side; real-audio fixtures in `fixtures/`), `audio/cues`, `audio/calibration` (latency measurement), `storage/` (Dexie repositories, backup import/export with validation), `diagnostics/` (the diagnostic journal, see below).
- `src/lib/composition/createApp.ts` — the composition root: wires real adapters into `createAppServices`. Called once in `src/routes/+layout.svelte`.
- `src/lib/ui/` — `primitives/` (Pixel* components, `VerdictSprite`), `play/` (`PlayScreen`, lane, mode-2 `answer/` pad, `PlayFrame` and the `views/` registry), `screens/<name>/` (home, summary, map, calibration, settings). Each screen has a `messages.ts` using `defineMessages({ fr, en })` from `$lib/i18n/index.svelte`; locale comes from stored settings.
- `src/routes/` — thin pages that pull `useAppServices()` and render a screen. `/dev/*` (screens with fake services) and `/diagnostic` are gated by `requireDev()` and 404 in production.

Tests use fakes from `src/lib/testing/fakes.ts` (`FakeClock`, fake metronome/detector/repositories). Repository behavior is specified by reusable contract suites in `src/lib/infrastructure/storage/testing/`, which the Dexie repository specs run.

## Rules that span files

These are fixed product decisions documented in `docs/superpowers/plans/README.md` (read it before changing scoring, timing or audio behavior). All numbers are named constants meant to be tuned, not inlined.

- **Times**: audio scheduling uses `AudioContext` seconds; scoring windows and reaction times are in ms. Onsets are corrected by the calibrated latency before judging.
- **Metronome**: a session's first start waits for `clock.settle()` (a fresh audio output loses its first sounds: `WebAudioClock` waits until it has played `OUTPUT_WARMUP_S`, so the counted bar's downbeat is heard); start at `clock.now() + 0.1` at the earliest; beats already past are dropped. `onBeat` can fire up to 100 ms _before_ the beat — never assume `clock.now() >= beat.time`, compare beat indexes with `>=`, never `===`. Tempo cannot change while running (`setTempo` throws). `at(time, callback)` wakes the session once the audio clock reaches `time`, at the scheduler's next wake-up (never early, at most `DEFAULT_LOOKAHEAD_MS` late), after that wake-up's beats; `stop()` or the returned function cancels it. `FakeMetronome.flush()` interleaves beats and wake-ups in the order they come due.
- **Bar grid** (mode 1): the target always lands on beat 1 of a bar (`alignedPromptBeat` in `domain/timing/grid.ts`); `LEAD_STEPS = [8, 4, 2]` (never 1), so prompts fall on beat 1 or 3. After a target the next prompt waits `RESPIRATION_BARS` (the breathing bar), where a miss shows the right answer (`VerdictView.correction`). The string shows `STRING_PREVIEW_BEATS` before the note (`PlayView.preview`). A lead change between sequences, like a change of scene, is a counted bar (`PlannedItem.countIn`). A `countIn` item may ask `restBars` of silence before its counted bar (the click muted, given back on the beat before the count or on pause); the link asks it at each new chord or set.
- **First note is the answer**; later notes are ignored. The window opens `MIN_RESPONSE_MS` after the prompt: earlier notes belong to the previous prompt and never answer this one. Mode 1 verdicts: wrong pitch/no answer → `wrong`, `|offset| ≤ PERFECT_WINDOW_MS` → `perfect`, else `early`/`late`. Past `LATE_LIMIT_MS` the detector keeps listening for `LATE_CAPTURE_MS`, bounded by the next prompt's string preview (`lateCaptureEnd`): a right note there is `offbeat` (correct, graded Hard, never direct recall — `beatTiming.isDirectRecall` checks it, lengthens the lead), a wrong one stays `wrong`. The attempt is stored once the capture settles. Order: perfect > early/late > offbeat > corrected > wrong (`corrected`: a triad anchor's wrong first chord put right later in the band; `correct: false`, a miss everywhere, only the screen salutes it). `isSuccess` (correct and not offbeat) is the success used by stats, grades and pacing. Mode 2 has no `early` and no `offbeat`.
- **Cold vs hot**: only cold attempts feed retention, FSRS and mastery. A free-play attempt on a learned card untouched for `MIN_COLD_DELAY_MS` is cold too. Deliberate exception: a probe is cold only when passed; a missed probe is stored hot because it measures no forgetting (`probeTemperature`, the only place that decides it).
- **Sessions** are `'learn' | 'free'` for the notes, `'triads' | 'triads-zone'` for the triads (one exercise per session, `createTriadSelector({ mechanic })`; the zone shows on the home screen once `triadZoneOpen`). Free play runs a fixed list (`createListSelector`); learn runs `createLearnSelector` (`progress/learnSelector.ts`): retests, cold reviews, resumed notes, new notes from `introductionOrder()`, then consolidation, for `LEARN_SESSION_MS`. A new note is first served as an unaided `'probe'`: a direct recall makes it a review card (`probeCard`), a miss brings the aided presentation on the next prompt. Inside a category the draw is random (injected `random`, `progress/order.ts`): never the previous card, never its mirror (`music/mirror.ts`), another string when possible; a note waits in the queue while its mirror is not acquired. New notes also need `NEW_NOTE_MIN_CARD_SUCCESS` on every note being learned and `NEW_NOTE_MIN_SESSION_SUCCESS` over the last `SUCCESS_WINDOW` mode 1 prompts (`progress/success.ts`); a miss (probes left out) brings a solid card next as hot `'consolidation'` (recovery); hot prompts stay within `MAX_WORKING_SET` cards. Sequences of `SEQUENCE_LENGTH` prompts at one lead and scene are a trial isolated in `progress/sequence.ts` behind `SEQUENCES_ENABLED`. The tempo is per exercise, not a setting (`settings.tempoBpm` is gone, nor is it in the Settings screen): each exercise has a `Progression` (`progressions` store), `startTempo` picks the tempo of an execution (own progression, else the definition's start tempo, else the last tempo on the same mechanic, else `DEFAULT_TEMPO_BPM`), and at the end of a learn session `nextTempo` (`domain/exercise/tempo.ts`) writes the next one, within `[TEMPO_MIN_BPM, TEMPO_MAX_BPM]` (80–160); the tempo never changes during a session. A tempo may have a generic, optional scope: `Execution.scope`, `Progression.scope`, `PlannedItem.tempoScope`, stored on the attempt as `Attempt.tempoScope`; `startTempo(definition, progressions, scope)` and the end-of-session write work per (exercise, scope), the controller matches a prompt to its execution by both (another scope's tempo restarts the metronome as another exercise's does), and a new scope starts at the definition's start tempo, never at another scope's. Without a scope, everything is as before. The gesture track scopes its grid exercises by grid (a ballad and a blues progress apart); the link has one tempo. Specs: `docs/superpowers/specs/2026-10-02-apprentissage-design.md`, `docs/superpowers/specs/2026-10-03-sondage-avant-apprentissage-design.md`, `docs/superpowers/specs/2026-10-04-rythme-et-consigne-design.md`.
- **Gesture track** (spec `docs/superpowers/specs/2026-10-10-voie-geste-design.md`): session kind `'gesture'` (`createGestureSelector`, `progress/gestureSelector.ts`), one mechanic `chord-grid` (`domain/mechanics/chordGrid.ts`, `learner: 'skill'`: attempts kept with their observations, no card) for four exercises in the order of the ladder, `gesture-link`, `gesture-climb`, `gesture-zone`, `gesture-jam` (`domain/gesture/`: elements, `linkShapes`, `nextZone`, opening from the triad cards acquired, `passageSucceeded` at `PASSAGE_SUCCESS`, `summarizeGesture`). Grids are data written with real symbols (`domain/grid/`: `iohefy-a`, `blues-f`; `parseChordSymbol` over the `SUFFIXES` table, `triadOf` over `TRIAD_OF_QUALITY`, `gridChanges` merges equal symbols in a row); `QUALITIES` holds triads and sevenths, triad code keeps `isTriadQuality`. A passage is a grid played once; each change is an attempt (`ChordGridItem`, key `${element}#${index}`). Rounds of a passage hand over without a gap: `createGridTiming` (`domain/timing/gridChange.ts`) gives each round a `handover` (the next change minus `min(GRID_EARLY_MS, GRID_EARLY_MAX_BEATS` beat`)`); the controller wakes there (`metronome.at`), withdraws the expectations, settles the round (`abandon(now)`), and opens the next change at once (`chained`) unless it has `countIn`, another tempo or another scene. A round with a handover never moves on by `after().advanceAt`; pause, quit and finish cancel the wake-up. In a climb, at a change where no shape of the chord on the set lies strictly beyond the last shape heard, the direction turns there and for the rest of the passage (`climbDirection`, computed by the selector and carried on the items, so the judge stays pure; the aid follows it); passages alternate by their starting direction. Zones span `ZONE_FRETS` frets; an open string counts inside the zone at fret 1 only; the rotation visits every start from 1 to `MAX_VOICING_FRET − ZONE_FRETS + 1`, `ZONE_STEP_FRETS` (5) apart modulo the starts, skipping a zone where a chord of the grid has no shape (`nextZone`, `domain/gesture/passages.ts`). What the implementation decided against the spec is listed in its section « Réalisation ». The home screen offers « Geste » once `AppServices.gesture().open`; the summary sums a gesture session up by exercise and grid (`SessionSummary.gesture`) with « Joué juste » on its misses (`AppServices.contest`).
- **Play views**: a presenter may give an opaque screen model (`MechanicPresenter.stage`), set by the controller in `PlayView.stage` with the view its exercise names (`ExerciseDefinition.view`, default `DEFAULT_PLAY_VIEW` = `'grid-scroll'`): for the prompt waiting before a counted bar, at the round's opening, and once settled. `ui/play/PlayFrame.svelte` (start, pause on Space, quit, countdown, « Joué juste » on Enter, audio error, fatigue) shows the view from the registry `ui/play/views/index.ts` (`PLAY_VIEWS`); `/session` uses it for `gesture` only, notes and triads keep `PlayScreen`. `GridScrollView` places chords through the pure `views/gridScroll.ts`. The link has its own view, `link-lane` (`LinkLaneView`, pure placement in `views/linkLane.ts`, model `LinkLaneModel`): the notes' lane, a tile per beat, the root or ↗/↘ on the first beat of each bar, the change asked due, the next tour drawn after the last bar; the neck with the notes in circles only when aided. A link tour that fails is played again at once, chained (`ChordGridItem.continued`: no counted bar, its lowest shape not played twice) until one succeeds; a link change is aided from `LINK_AID_AFTER_MISSES` misses in a tour until a tour succeeds (this session only). A relation may give `TimingRelation.targetOffset`: the controller then takes its earliest beat as the target's and counts the bar down to the target (the grid opens a beat before its change, the count still ends on the change). An exercise may carry `howTo` (data, fr/en): before its first prompt in a series the controller stops (`PlayView.briefing`, status paused, `resume` goes on with a counted bar at its tempo); the first one is told on the start screen through `ready()`. `/dev/gesture` plays the link (`?view=grid`: a climb).
- **Mechanics and exercises**: the core (controller, recorder, rounds, sensors) never names `'locate'` or `'identify'` (nor any other mechanic). A mechanic is a `MechanicRules` (domain) plus a `MechanicPresenter` (application); the neck's two live in the closed `NeckCard` union, allowed only in the neck's own domain (selectors, introduction queue, mirrors, stats, neck map). To add a mechanic: write its rules and add them to `domain/mechanics/index.ts` (`mechanicRules`, used by backup validation and migration), write its presenter and add it to `SessionDeps.mechanics` (wired in `createApp`), and add a `SensorFactory` to `SessionDeps.sensors` when it needs a new sensor. `application/session/thirdMechanic.spec.ts` plays a fake mechanic end to end to keep that promise. Attempts carry `exerciseId`, `mechanic`, `tempoBpm` and a mechanic-specific `data`.
- **Storage**: Dexie version 7 (adds the `scopedProgressions` table, keyed `[exerciseId+scope]`, beside `progressions` for an exercise's own tempo; `DexieProgressionRepository` routes by scope); version 6 added `observations` on attempts and `latencyMs` on sessions; version 5 added `progressions` and reshaped cards and attempts by mechanic and exercise). Backup is version 3; version 2 and 1 files are still imported and migrated (`legacy/v2.ts` `fromV2`).
- **Observations**: an attempt keeps every raw observation its sensors perceived during its _span_, from the opening of its round to the opening of the next round (or pause, or end), so it covers the breathing bar and counted bars (`ObservationSpan`, `application/session/observationSpan.ts`). An observation belongs to the span open _on arrival_, not by timestamp; `atMs` is ms since the prompt (round audio time), latency removed, negative when before. Each one records its `fate` (`answer`, an `IgnoreReason`, `other-sensor`, `unreadable`) and the judge's `correct` at play time (null when unreadable or from another sensor). Detector rejections (`NoteDetectorPort.onRejected`: `no-pitch`, `unclear`, `unstable`, `out-of-range`) are stored as `'unreadable'` and are never answers (`Observation.readable`). The attempt is written at the verdict with a snapshot; `AttemptRecorder.completeObservations` rewrites the final list when the span closes (`setObservations`), and `finish()` awaits them. `observations: null` marks attempts from before this existed. The sensor payload is stored as emitted and not validated by storage. `SessionRecord.latencyMs` keeps the calibration offset used. Spec: `docs/superpowers/specs/2026-10-06-journal-observations-design.md`.
- **FSRS** runs without learning steps (`learning_steps: []`): a first Good sends a card to Review. Cards stored at the old 1-beat lead move to 2 (Dexie version 4, and on backup import); attempts keep their recorded lead (`RecordedLeadBeats`).
- **Drawn string** (`ui/play/StringDiagram.svelte`, `STRING_DIAGRAM_AID`): a removable aid (`PlannedItem.stringAid`) on the aided presentation and on the next hot prompt after a miss of that card in the session, gone after `STRING_AID_FADE_SUCCESSES` success; never on reviews or probes. Setting the constant to false removes it; nothing else depends on it. Confusions include `'string-name'`: the open note of the prompted string played instead of the target.
- **Open strings** (fret 0) are never prompted: the prompt names the string by its open note.
- **Chord sensor** (spec `docs/superpowers/specs/2026-10-07-capteur-accords-design.md`): a mechanic gives its sensor an expectation per round (`MechanicPresenter.expectation?` → `ObservationSource.expect?`, opaque to the core); `chordSensor` turns reports into observations. Expectations are withdrawn (`expect(null)`) before a span closes, so a window cut short reports into its own round. The ringing previous chord is never a candidate. The verifier judges each attack from `FIRST_READING_MS` every `JUDGE_EVERY_MS` until a reading is final (expected shape, the same shape `STABLE_READINGS` times, nothing at `NOTHING_FINAL_MS`, or the last one), then stops; a new attack closes an earlier window only once it is older than `ARPEGGIO_SPAN_MS`, so an arpeggio stays whole and a chord played again later is read apart (known risk: a chord played again within that span is read with the first). In the anchor the first chord is the answer: a wrong one shows at once as a provisional miss (`Round.observe` may return `provisional`), and a later right attack in the band settles `corrected` (spec `docs/superpowers/specs/2026-10-09-retours-voie-memoire-design.md`). After a miss, the triad presenters draw what was heard and expected (`MechanicPresenter.feedback`, `VerdictView.heard/expected/gap`) with `ChordShape`, in the style of `Settings.chordDiagram` unless the exercise imposes `ExerciseDefinition.chordDiagram`; a contestable mechanic's miss can be contested in play (« Joué juste », Enter; `PlayView.contest`, `contest()`), until the next prompt. Known risk: D 2-3-2 right after a ringing 7-7-5 is falsely taken for 11-10-10 (frozen fixture).
- **Diagnostic journal** (spec `docs/superpowers/specs/2026-10-07-journal-diagnostic-design.md`): kept apart from learning data, in its own IndexedDB (`neckspert-play-diagnostics`), never in the backup. Only adapters write to it (`DiagnosticSink`: `WebAudioInput`, `DiagnosticAudioRecorder` at 16 kHz, `NnlsChordVerifier` with expectations, full reports and spectra); the core and the mechanics never see it. A take runs from the input's opening to its closing; joins with attempts are made by time at analysis. `Settings.diagnostics` (`enabled: null` = on in dev builds, off in published ones; budget in MB, oldest closed takes pruned). Export: a STORE zip built take by take (`exportArchive.ts`). `ChordReport` carries no spectrum: attempts stay small.
- **Audio input** is opened raw (no echo cancellation / noise suppression / AGC), except the Firefox-on-macOS built-in mic workaround in `WebAudioNoteDetector`. The metronome click is pitchless filtered noise so the detector ignores it; verdict cues are < 150 ms and play after the answer.

## Visual system

`DESIGN.md` is the source of truth: a Game Boy world in exactly four tones (`#E99568`, `#BE6754`, `#813B2A`, `#451218`), a fifth only as a checkerboard of two adjacent tones, one pixel face (VT323), 8 px tile spacing. Tokens live in `src/lib/ui/tokens.css` (`--np-*`); use them rather than raw values. Per-screen design contracts and approved mocks are under `.impeccable/surfaces/` and `.impeccable/mocks/` (the play screen contract is `.impeccable/surfaces/src-routes-session-page-svelte.md`). `prefers-reduced-motion` must drop the verdict pop.

## Workflow conventions

- Implementation plans and specs live in `docs/superpowers/plans/` and `docs/superpowers/specs/` (dated, in French). Plan work historically ran in git worktrees under `.worktrees/` on `plan/<id>` branches.
- Commit messages: Conventional Commits, lowercase, imperative and behavior-focused (`feat: open the summary when free play ends`, `fix: …`, `test: …`, `docs: …`).
- TDD for any logic: domain and application code each have colocated `*.spec.ts`.
