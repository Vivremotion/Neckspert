# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A fretboard-memory trainer for guitarists, built as a rhythm game. The player hears a metronome, sees a prompt ("F, corde de B"), and plays the note on a real guitar on the beat (mode 1, _locate_), or taps the note name for a given string/fret (mode 2, _identify_). Spaced repetition (FSRS via `ts-fsrs`) decides what comes back; only the first, _cold_ attempt at a card after a delay feeds retention stats. Read `PRODUCT.md` for the product rules and `docs/projet.md` for the project (product, principles, engine, exercise language); the order of work is in `docs/feuille-de-route.md`, the backlog in GitHub issues. Product docs, plans and UI copy are in French; code, identifiers and comments are in English.

## Architecture

Svelte 5, runes only (forced for all non-`node_modules` files), SvelteKit with `ssr = false`, no component library, native CSS with variables. Layered, ports-and-adapters:

- `src/lib/domain/` — pure logic, no Svelte, no browser APIs. `types.ts` holds the shared domain model (cards keyed by `cardKey(skill, itemKey)`).
- `src/lib/application/` — `ports/` defines the interfaces infrastructure must implement. `app.ts` defines `AppServices`, the single object screens consume, provided through Svelte context (`provideAppServices` / `useAppServices`). `session/contract.ts` defines `PlaySessionController` and its reactive `PlayView` — the contract between orchestration and the play screen.
- `src/lib/infrastructure/` — adapters. One `WebAudioClock` owns the single `AudioContext`; one raw `WebAudioInput` is shared and its frames feed every detector. A played note is an attack of the attack sensor and the pitch read after it. Diagnostic journal and audio-input rules: `src/lib/infrastructure/CLAUDE.md`.
- `src/lib/composition/createApp.ts` — the composition root: fills the registries from the catalog (`loadDefinitions`, `composition/definitions.ts`, only if nothing is loaded yet) and wires real adapters into `createAppServices`, with the definitions service (`application/definitions/service.ts`). Called once in `src/routes/+layout.svelte`, which awaits `services.definitions.ready()` before its first screen.
- `src/lib/ui/` — `notation/` is the only VexFlow importer, loaded lazily; `notationReady()` awaits the embedded Bravura font before engraving. Visual system: `src/lib/ui/CLAUDE.md`. Each screen has a `messages.ts` using `defineMessages({ fr, en })` from `$lib/i18n/index.svelte`; locale comes from stored settings.
- `src/routes/` — thin pages that pull `useAppServices()` and render a screen of `ui/screens/` (the home `/`, the Library `/library`, the summary, the neck map `/map`, the settings). `/dev/*` (screens with fake services) and `/diagnostic` are gated by `requireDev()` and 404 in production.

Tests use fakes from `src/lib/testing/fakes.ts`. The registries start empty: a setup file of both projects (`src/lib/testing/setup.ts`) fills them from `catalog/` before every test file, and specs name the catalog's exercises and grids through `src/lib/testing/catalog.ts` and its ids through `src/lib/testing/catalogIds.ts` (the code outside tests and migrations names none, see « Skills, item sets and exercises »). Repository behavior is specified by reusable contract suites in `src/lib/infrastructure/storage/testing/`, which the Dexie repository specs run.

## Rules that span files

These are fixed product decisions documented in `docs/superpowers/plans/README.md` (read it before changing scoring, timing or audio behavior). All numbers are named constants meant to be tuned, not inlined.

- **Times**: audio scheduling uses `AudioContext` seconds; scoring windows and reaction times are in ms; musical positions and durations are exact fractions of a whole note (`domain/time/`). Onsets are corrected by the calibrated latency of their sensor before judging: `Settings.latency` holds one `SensorLatency` per sensor (`note`, `chord`, `attack`…) with its provenance (`'system'`: measured without the player's gesture; `'player'`: from the player's attacks on the click). The calibration (`audio/calibration/CalibrationService`) measures it without the player: the computer's mic, a second `WebAudioInput` in the same context opened `raw`, is calibrated on clicks heard in silence (`loopLatency`: only clicks heard at one common delay count, with a minimum share and a spread limit), then the interface is compared with it on notes played freely (`pairedDelay`: constant offset found wide, then one-to-one pairs, a minimum of pairs and a spread limit); with the built-in mic alone, the click loop is the latency and a separate bleed check follows, headphones back on; `note` = `chord` = `attack` + the note detector's delay, anchored on the notes (0: a note takes its attack's time; the chord verifier's own onsets, within 6 ms of the attacks, are neglected); the reference mic's tracker is more sensitive (`REFERENCE_ATTACK_CONFIG`). It never falls back by itself: a failed reference ends with `reason: 'reference'` and its numbers, and the calibration on the click (`runOnClick`, `player` for all, notes within `PLAY_MAX_OFFSET_MS` of a click) is the player's explicit second choice; the screen shows the measure (`CalibrationMeasure`). `run(deviceId, onProgress)`; the page writes the device, `latency` and `clickBleed` together, only on success. A sensor without a latency of its own takes its fallback's, as provenance `player` (`sensorLatency`, `session/latency.ts`; `LATENCY_FALLBACK`: `attack` → `note`). `Settings.clickBleed` (click heard on the playing input) makes the start screen ask for headphones when the rounds listen with a sensor the click would fool (`asksForHeadphones`, `session/clickBleed.ts`: the `attack` and `note` sensors; `PlayView.audioError: 'bleed'`), the first how-to still shown below; the series is not refused.
- **Metronome** (the click is one of the transport's sounds; there is no metronome port since H5, see « Musical time »): a session's first start waits for `clock.settle()` (a fresh audio output loses its first sounds: `WebAudioClock` waits until it has played `OUTPUT_WARMUP_S`, so the counted bar's downbeat is heard); the transport starts at `clock.now() + START_DELAY_S` (0.1) at the earliest; a sound whose time is past is dropped, not played late. `Transport.at(bar, callback)` (over `SoundSchedulerPort.at(time, callback)`) wakes the session once the audio clock reaches that time, at the scheduler's next wake-up (never early, at most `DEFAULT_LOOKAHEAD_MS` late); the returned function or `cancelAll` cancels it. The tempo changes only over bars not yet scheduled (`changeTempo` and `changeMeter` throw otherwise). `FakeSoundScheduler.flush()` runs the wake-ups due, earliest first. The clock's `epochNow()` is the wall time before the audio context exists, so a cold load of `/session` shows its start screen (the context is created by Start).
- **Bar grid** (mode 1): by default the target lands on beat 1 of a bar; a plan may say where its round starts in the bar (`RoundPlan.barOffset`, written by an exercise in its `round` template) and where its count ends (`countEndsOn`: `'prompt'` by default, `'target'` for a grid change; written by an exercise in its `round` template); a round is never placed with its prompt already past (`comingStart`, a bar later while it would be). Leads come from the exercise's ladder (locate 8, 4, 2: prompts on beat 1 or 3); a lead, like a beat-valued window, may be any exact fraction of a beat (`beatsOf`/`isBeatCount` in `domain/time/meter.ts`, over `Fraction.fromNumber`, shared by the round compiler and the validation). Where the next round goes is decided in one pure function (`placeNext`, `series/placement.ts`: chained, after the breath, at the next beat, or after a counted bar). One rule places every timed round without a handover (`timedStart`): the first start ≥ `earliest` (end of the counted bar, or of the previous round, whose plan ends with its exercise's breath, `params.pacing.respirationBars`, default `DEFAULT_RESPIRATION_BARS`) that lies `barOffset` into its bar and, when the count ends on the prompt, whose prompt is not before `earliest`; a free-time round (identify) opens at the next beat (`nextBeat`) and settles at its answer, the tempo map running on. In the breath a miss shows the right answer (`VerdictView.correction`); the next item shows its `previewBeats` before its prompt (the exercise's `flow.previewBeats`, else the presenter's, resolved once by `previewBeatsOf` and read by the template as `{ param: 'previewBeats' }`, 0 without one: `DEFAULT_PREVIEW_BEATS` for locate, the string alone), the settled round staying until then. The triads place by the same rule (the anchor: its root on the target, its chord's band to the end of the bar). A change of scene is a counted bar (`PlannedItem.countIn`), and so is a change of meter: the series plays each item in its exercise's meter and moves to another with `Transport.changeMeter` (positions go on, the part of a bar before the new meter's first whole bar stays silent), chaining only within one meter. A `countIn` item may ask `restBars` of silence before its counted bar (the click muted, given back on the beat before the count or on pause); a passage source asks it (`passages.restBars`, the link 1) before every passage that follows another of the session, except one played again by `again`.
- **First note is the answer**; later notes are ignored. The windows are exercise data (`params.windows` over `DEFAULT_RESPONSE_WINDOWS`, read by the template as `{ param: 'windows.…' }`). The window opens `minResponseMs` after the prompt: earlier notes belong to the previous prompt and never answer this one. Mode 1 verdicts: wrong pitch/no answer → `wrong`, `|offset| ≤ perfectMs` → `perfect`, else `early`/`late`. Past `lateMs` the round keeps listening for `lateCaptureMs`, bounded by where the next expectation is due and by the end of listening (`listenUntil`: the next prompt's string preview for locate, the round's end for the triads; `responseZones`, `domain/time/modes/firstAnswerTimes.ts`): a right note there is `offbeat` (correct, graded Hard, never direct recall — `isDirectRecall` of the `response` verdict checks it; it counts as a miss for its level), a wrong one stays `wrong`; an attack goes to the earliest unanswered expectation whose zone holds it. The attempt is stored once the capture settles. Order: perfect > early/late > offbeat > corrected > wrong (`corrected`: a triad anchor's wrong first chord put right later in the band; `correct: false`, a miss everywhere, only the screen salutes it). This one-answer verdict is `ResponseVerdict`. Every attempt stores `success` (the relation's word on whether the round passed), `correct: boolean | null` (the judge's word on the content; null when nothing was judged, as in a rhythm cycle; a cycle with content is correct when no expectation is `wrong-pitch` or `missed`), `verdict` as an envelope `{ relation, version, value }` (`responseVerdictOf` reads it back for the response relations `RESPONSE_RELATIONS`), `measures` and the resolved `plan` (`RoundPlanRecord`, `series/recordResponse.ts`: the plan in JSON, its `startAudioS`, its `tempo`, the `thresholds` its verdict read; `roundPlanFromRecord` reads it back). Every settled round is written one way (`roundAttempt` over `recordedAttempt`; a round judged by the cycle verdict keeps `FigureAttemptData`: item, level, report). `Attempt.success` is what stats, grades and pacing read, never `correct` (`domain/successBoundary.spec.ts`); for a response round the `response` verdict mode decides it (correct and not offbeat, `domain/time/modes/responseVerdict.ts`), and direct recall reads it (`directRecallOf`, the subject's `recall`). Mode 2 has no `early` and no `offbeat`.
- **Cold vs hot**: only cold attempts feed retention, FSRS and mastery, and an attempt counts cold only when played at a ladder level that asks a direct recall (`success: 'direct-recall'`, `asksDirectRecall`, `domain/learning/ladder.ts`; `AttemptRecorderDeps.countsCold`, given by the memory sessions from the exercise's ladder; an item without a level never counts cold): at any other level a review or a free-play attempt is stored hot and leaves its card's scheduling as it was (decision 12 of issue #19). A free-play attempt on a learned card untouched for `MIN_COLD_DELAY_MS` is cold too, at such a level. A ladder with no such level never feeds memory, and is not refused. There is no probe any more (issue #19): attempts stored before keep the phase `'probe'` (`RecordedPhase`, the served phases being `ItemPhase`).
- **Sessions** start from a routine or from one exercise alone (`SessionOrigin`, `{ routine, free? } | { exercise, free? }`, `domain/types.ts`, recorded as is on `SessionRecord`; the code has no session kind since chantier 2's plan 5a, `noSessionKind.spec.ts`; `/session?routine=<id>`, `&free=1`, or `/session?exercise=<id>`, read by `sessionFromQuery`, anything else « Séance introuvable »). A routine is a home entry written in a definition file's `routines` (`RoutineDefinition` `{ id, title, exercises, howTo?, opens? }`, `domain/routine/`: `routineFromJson` (shape, `MAX_ROUTINE_EXERCISES` 32, `MAX_OPENING_TERMS` 16, `MAX_OPENING_DEPTH` 4), `routineProblem` (exercises defined, not mixing skills with and without cards, no skill practised twice, one without cards writes `passages`, the opening's names defined), `registerRoutine`/`findRoutine`/`routines`, `opened` over `Known`; registered after every exercise of its source; the catalog's four in `catalog/routines.json`, whose order is the home's: `notes`, `chords`, `chords-zone`, `changes`; format in `docs/fichiers-de-definitions.md`). What its session draws is deduced from its exercises, no routine named (`AppServices.startRoutine(id, { free? })`): all on skills with cards → the learning procedure on `exerciseSubject` over them in the routine's order (the first with a ready item introduces), reading the cards and attempts of their skills and of those `params.learning.enter` names, or with `free` a fixed list (`createListSource` over `buildFreePlan`, `domain/progress/plans.ts`: `FREE_PLAY_COUNT` items drawn among the items the exercises list, each at the lead and level its `LevelState` holds, `freeLeadOf`/`freeLevelOf`); all writing `passages` → `createPassageSource`, each in turn in the routine's order. `AppServices.startExercise(id)` plays any exercise alone: a memory exercise freely on its own items (`{ exercise, free: true }`), a passages exercise through the passage source, any other as an exercise session (see « Exercise sessions »). `AppServices.routines()` tells the home each registered routine (`RoutineEntry`: `open` when every exercise is defined and either one of its skills holds a card its exercises serve, or it has something to play (a card or a ready new item; an open passage index, `passagesOpen`) and `opened(opens)` holds, an `acquired` term counting the served cards marked acquired, a `level` term the `LevelState.level + 1` of its (exercise, scope); `due` and `nextReviewAt` for a memory routine); the home lists the open ones only, in order, and nothing else (Space and « Commencer » start the first; with none open, « Rien à jouer pour l’instant » and a link to the Library, no « Commencer »; a routine whose entry throws is told closed and logged, `[home] <id>: cannot tell whether it opens`, the others still told), `/session?routine=` does not read the opening. The Library (`/library`, `ui/screens/library/`, `AppServices.library()`, `LibraryEntry`) lists every registered exercise, none filtered or ranked, in the routines' order (each routine's exercises as it writes them, each once) then those no routine lists, in the order registered (`libraryOrder`): its title (`exerciseTitle`), the titles of the routines that list it, and `playable` (`playableAlone`: `aloneSourceOf`, `domain/exercise/registry.ts`, is `memory` (a skill with cards and listed items), `passages` with an open index (`passagesOpen`), or `cycles` (`playsInExerciseSession`); a throw is logged, `[library] <id>: cannot tell whether it plays`, and told not playable); a playable entry links to `/session?exercise=<id>`, another says « Rien à jouer pour l’instant »; with no exercise registered it says « Aucun exercice. ». Playable implies that `startExercise` starts it, not the converse: a passages exercise with no open index starts and ends at once on the summary. The notes' mixed free play (`/session?routine=<id>&free=1`) works but has no link any more. The summary (`AppServices.sessionSummary`, `SessionSummary`, `ui/screens/summary/`) has one shape for every session: `exercises`, one `PlayedExercise` per (exercise, scope) with a round, in the order first met (`summarizePlayed`, `domain/session/played.ts`: `rounds`/`passed`, only the changes on a line that played passages; `level`, only for the exercise played alone whose round writes a figure, from `summarizeExercise`; `tempo` first and last; `inPassages`; `passages` played and passed at its `passages.passes`, null for an exercise no file defines), the contestable missed changes (`misses`, `summaryMisses`, `domain/session/misses.ts`), and, for a session not of memory still in `SessionMemory`, `series` and `replayable`; `memory` (its skills have cards, or nothing tells otherwise) draws the memory block instead, its next review counted on the cards the session's exercises list (`cardsListedBy`, the helper the home's routine entries use); an exercise no file defines keeps its line, titled by its id. The home shows no offset to the beat over all sessions nor its trend any more (`homeStats`, `computeHomeStats` and the trend are gone); a memory session's summary still shows that session's offset. A series is drawn only when it has a run. Every session plays on `SessionController` for the `durationMs` their preparation returns (`SESSION_MS` for every session, written in `createAppServices`; no round that does not continue a handover starts after it), each item a round compiled from its exercise's `round` template (`compileRound`, `domain/exercise/round/`) at its level's lead. The learning procedure (`createLearningProcedure`) serves retests, cold reviews, resumed notes, new notes, then consolidation. A new item is served as `'learning'`, hot, at level 1 of its ladder (index 0), with the screen that level writes: there is no probe (issue #19). A due card at a level that asks no direct recall is caught up once in the session in place of its review, as a hot `'consolidation'`, outside the cold cap (`coldCap`) and within the working set (`maxWorkingSet`). Inside a category the draw is random (injected `random`): never the previous card (`allowedAfter`, `procedure.ts`, for any exercise). A new item comes from the lists its exercises write (see « Skills, item sets and exercises »): there is no mirror rule, no preference for another string, and the notes of the triads being learned no longer come first. New notes also need `NEW_NOTE_MIN_CARD_SUCCESS` on every note being learned and `NEW_NOTE_MIN_SESSION_SUCCESS` over the last `SUCCESS_WINDOW` mode 1 prompts (`progress/success.ts`); a miss brings a solid card next as hot `'consolidation'` (recovery); hot prompts stay within `MAX_WORKING_SET` cards (these constants are the defaults of the set's settings, see below). The tempo is per exercise, not a setting (`settings.tempoBpm` is gone, nor is it in the Settings screen): an exercise writes `tempo` (a number, beats of its meter per minute; absent: `DEFAULT_TEMPO_BPM`, 80), which its exercise levels may override like any parameter (`tempoOf(definition, exerciseLevel)`; see « Skills, item sets and exercises »); locate, identify and the triads write no levels and play at 80 bpm. An exercise level is held per (exercise, scope) in a `LevelState` (item `''`, stored only for an exercise that writes levels), read once per series and moved by every settled round (`ExerciseLevels`, `series/exerciseLevels.ts`, over `nextLevelState`); a level reached applies at the next round that does not chain (after a breath or before a counted bar), announced (`PlayView.announcement`), with a counted bar at its tempo; a chained round keeps the level of its run, and the next session starts at the level reached. A scope is generic and optional (`PlannedItem.scope`, stored as `Attempt.scope`); another exercise's or scope's tempo brings a counted bar at its tempo; the session record keeps one `Execution` per (exercise, scope) met, at the tempo of its first round (null in free time). The gesture scopes its grid exercises by grid (`passages.scope: 'grid'`: a ballad and a blues progress apart); the link has one level. Specs: `docs/superpowers/specs/2026-10-02-apprentissage-design.md`, `docs/superpowers/specs/2026-10-03-sondage-avant-apprentissage-design.md` (replaced by issue #19), `docs/superpowers/specs/2026-10-04-rythme-et-consigne-design.md`. One learning procedure (`domain/learning/`, `createLearningProcedure`) is driven by a `LearningSubject` built from the data of the session's memory exercises (`exerciseSubject`, `domain/learning/exerciseSubject.ts`; see « Skills, item sets and exercises ») and keeps one `LevelState` per item on the ladder its exercise writes (`params.ladder`, read by `ladderOf`: levels of `LadderParams`: lead, what the level shows (`presentation.*`), pass and drop, the top marked `success: 'direct-recall'` where only a direct recall counts), moved by `nextLevelState`; an item's settings (`retestGaps`: prompts before its next retest, `[0]` after its introduction and after a miss, `[1]` after a success, whatever its level) come from its exercise's `params.learning` (`itemLearningOf`), the set's (slots, working set, introduction thresholds, consolidation, category `order`, `recoveryAfterMisses`…) from the session, `createLearningProcedure({ set })`, today `DEFAULT_SET_LEARNING`; what counts as a direct recall is the skill's data (`SkillDefinition.directRecall.withinMs`, read by `directRecallOf(skill)`, and in a round template as the param `directRecall.withinMs`; an item has cards when its skill is registered with `memory`, `hasCards`), `ItemSource` names every item source and `choose` picks a series among candidates. A level held above the ladder's top (`ladderLevel`) is served at the top, and every attempt writes the level played. The triads' rules (a new chord shown at level 1 from its first prompt, never the same voicing twice, the zone asking only chords acquired in the anchor and another shape than the last) are played end to end in `series/triadsSession.spec.ts`.
- **Gesture track** (spec `docs/superpowers/specs/2026-10-10-voie-geste-design.md`; its exercises are data since chantier 2's plan 4b, spec `2026-11-18-aucun-exercice-dans-le-code-design.md` § 7 and « Réalisation (plan 4b) »): the routine `changes`, served by `createPassageSource` (`domain/session/passageSource.ts`), four exercises in the order of the ladder, `inversion-run` (the link), `grid-in-direction` (the climb), `grid-in-zone` (the zone), `grid-reading` (the jam), each practising the skill of its name (`memory: false`: attempts kept with their observations, no card; the link's skill is on the set `placed-voicing`, the others' on `change`, `ChangeItem` `{ grid, index }`); `domain/gesture/` is gone (plan 5b), its summary now the one summary (see « Sessions »). Each writes `passages` (`PassagesTemplate`, `domain/exercise/passage/`: `passagesProblem`, `passageIndices`, `passageMembers`, `indexOpen`; format in `docs/fichiers-de-definitions.md`): a passage is the members of a family for one index, each the item of a round; the indices are the product of the lists of `of` (keyed `grid=iohefy-a;strings=3,2,1`); `members` is a selection without `of`, from a family that gives members from a passage index (`PASSAGE_DERIVATIONS`: `grid-changes`, `domain/families/music/gridChanges.ts`, a grid's changes; `chord-shapes`, a chord symbol's triad on a zone of strings, the link writing `order: ['position']`, `take: 4`, `andBack: true`), read with the params of level 1 and the passage params; `each` holds the passage params (`direction`, `zone`), each taking at every passage of an index the value after the one its last passage started with, read as `{ param }` by a selection only (a filter's value, `toward`, `take`; a number of the round, `prompt.lead` or `window.ms`, reading one is refused) and refused when anything else gives that name; `opens` (`{ acquired: { skill, item, need } }`: every member a round's content admits without filters, grouped by strings, acquired through the correspondence `item` in every group or one, `indexOpen`, its skill and correspondence checked by `passagesOpensProblem`); `again: 'until-passed'` (the link: a passage under `passes` comes back whole, with its values, after a counted bar); `restBars`; `passes` (0.9); `scope` (the `of` key that scopes the exercise level). Limits, each checked before the work it bounds: `MAX_PASSAGE_INDICES` 500, `MAX_PASSAGE_EACH` 64, `MAX_PASSAGE_MEMBERS` 256 (counted without the filters and take that read a passage param), `MAX_REST_BARS` 16, `MAX_GRID_CHANGES` 256 (`gridFromJson`), `MAX_PASSAGE_ROUND_CHECKS` 5 000 (the round of each member of each index's first passage, each passage param at its first value and the params of level 1, compiled at load by `passageRoundsProblem`, `validateExercise`, counted before any is compiled; an index whose first passage has no member or cannot be read, `isUnplayable`, is left to the source). Playability, the opening and the turn are read at level 1: a level that changes a param the content reads is played unchecked. The source plays the exercises in turn, each on its open index played least recently (the order written on a tie), read from `data.passage` (`AttemptPassage`, `passageOf`; changes stored before plan 4b carry none and are not read), skips a passage that cannot be played (no member, more than the limit, a round that does not compile whole, `compilePassageRound`, a round admitting nothing, `isUnplayable`) to the next values and leaves out for the session an index with none, or one whose failed tries in one `next()` have cost `MAX_PASSAGE_TRIES` (1 000, in `roundCheckCost` units plus a figure's notes, as at load); a playable passage is always served whatever it weighs, and `next()` answers null only when nothing is left (no cap per call: one `next()` pays every failing index it meets, about 1.9 s once for a file made of seven failing heavy exercises), counts in each passage's first round, and gives each round the member heard last in the passage (`PlannedPassage.previous`: whatever member of the family the answer names, `Family.named`, of any chord); where a `position` filter with `turns` finds nothing beyond it (`select`'s `turned`), the passage param its `toward` reads turns for the rest of the passage. Grids are data written with real symbols (`catalog/changes.json`: `iohefy-a`, `blues-f`; `domain/grid/`: `parseChordSymbol` over the `SUFFIXES` table, `triadOf` over `TRIAD_OF_QUALITY`, `gridChanges` merges equal symbols in a row); `QUALITIES` holds triads and sevenths, triad code keeps `isTriadQuality`. - **Observations**: an attempt keeps every raw observation its sensors perceived during its _span_, from the opening of its round to the opening of the next round (or pause, or end), so it covers the breathing bar and counted bars (`ObservationSpan`, `application/session/observationSpan.ts`). An observation belongs to the span open _on arrival_, not by timestamp; `atMs` is ms since the prompt (round audio time), latency removed, negative when before. Each one records its `fate` (`answer`, an `IgnoreReason`, `other-sensor`, `unreadable`) and the judge's `correct` at play time (null when unreadable or from another sensor). Detector rejections (`NoteDetectorPort.onRejected`: `no-pitch`, `unclear`, `unstable`, `out-of-range`) are stored as `'unreadable'` and are never answers (`Observation.readable`). The attempt is written at the verdict with a snapshot; `AttemptRecorder.completeObservations` rewrites the final list when the span closes (`setObservations`), and `finish()` awaits them. `observations: null` marks attempts from before this existed. The sensor payload is stored as emitted and not validated by storage. `SessionRecord.latencyMs` keeps the latency of the first sensor met in the series that has one calibrated (`sensorLatency`; 0 when none is; null only before latencies were kept). Spec: `docs/superpowers/specs/2026-10-06-journal-observations-design.md`.
- **FSRS** runs without learning steps (`learning_steps: []`): a first Good sends a card to Review. Cards stored at the old 1-beat lead move to 2 (Dexie version 4, and on backup import); attempts keep their recorded lead (`RecordedLeadBeats`).
- **Drawn string** (`ui/play/StringDiagram.svelte`; the `string` picture, which locate's ladder writes at its level 1 with the fret, `'presentation.picture': 'string'` and `'presentation.detail': '{fret}'`): drawn at the levels whose presentation names it, and nowhere else; it no longer comes back after a miss nor fades after successes (`STRING_DIAGRAM_AID`, `PlannedItem.stringAid` and `aidFadeSuccesses` are gone since issue #19). Confusions include `'string-name'`: the open note of the prompted string played instead of the target.
- **Open strings** (fret 0) are never prompted: the prompt names the string by its open note.
- **Chord sensor** (spec `docs/superpowers/specs/2026-10-07-capteur-accords-design.md`): a presenter gives its sensors an expectation per round (`SetPresenter.expectation?` → `ObservationSource.expect?`, opaque to the core; the `voicing-on-strings` presenter receives the round's compiled expectations and listens for the shapes the selection admits, the lookalikes around them as before; the changes' presenters likewise through `changeExpectation`, `application/sets/changeExpectation.ts`: the shapes their content admits, then look-alikes within `NEIGHBOUR_FRETS`, never a shape sounding the pitches of the one still ringing, the content's previous member); `chordSensor` turns reports into observations. Expectations are withdrawn (`expect(null)`) before a span closes, so a window cut short reports into its own round. The ringing previous chord is never a candidate. The verifier judges each attack from `FIRST_READING_MS` every `JUDGE_EVERY_MS` until a reading is final (expected shape, the same shape `STABLE_READINGS` times, nothing at `NOTHING_FINAL_MS`, or the last one), then stops; a new attack closes an earlier window only once it is older than `ARPEGGIO_SPAN_MS`, so an arpeggio stays whole and a chord played again later is read apart (known risk: a chord played again within that span is read with the first). In the anchor the first chord is the answer: a wrong one shows at once as a provisional miss (`PlanRound.observe` may return `provisional`), and a later right attack in the band settles `corrected` (spec `docs/superpowers/specs/2026-10-09-retours-voie-memoire-design.md`). After a miss, the lane draws what was heard and expected with `ChordShape` and tells the gap and the right shape (`CONTENT_VIEWS.member.miss` → `StageVerdict.misses`, drawn through `PICTURE_VIEWS`; a missed root tells its position), the changes' views likewise through the same `CONTENT_VIEWS.member.miss` (a content compiled in a passage carries `previous`, and its miss is told as a change's: the expected shape the admitted one closest to the one heard, else to the one ringing, else the lowest, `expectedShape`, no correction; a triad played in a passage would be told so too), in the style of `Settings.chordDiagram` unless the exercise imposes `ExerciseDefinition.chordDiagram`; a miss of an exercise whose presenter or `flow` says `contestable` can be contested in play (« Joué juste », Enter; `PlayView.contest`, `contest()`), until the next prompt. Known risk: D 2-3-2 right after a ringing 7-7-5 is falsely taken for 11-10-10 (frozen fixture).

## Workflow conventions

- The backlog is GitHub issues and the project board, not a file in the repository; issues are in French.
- How a ticket moves (columns, one ticket in progress per track, Definition of Ready and Done, questions as issue comments labeled `attend-auteur`, the handover comment, local previews on port 5200 + issue number via `scripts/preview.mjs`, continuous deployment from `main`): `docs/flux-de-travail.md`. Never decide a product or pedagogy question yourself: ask it on the issue.
- Implementation plans and specs live in `docs/superpowers/plans/` and `docs/superpowers/specs/` (dated, in French). Plan work historically ran in git worktrees under `.worktrees/` on `plan/<id>` branches.
- Commit messages: Conventional Commits, lowercase, imperative and behavior-focused (`feat: open the summary when free play ends`, `fix: …`, `test: …`, `docs: …`).
- TDD for any logic: domain and application code each have colocated `*.spec.ts`.
