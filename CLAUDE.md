# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A fretboard-memory trainer for guitarists, built as a rhythm game. The player hears a metronome, sees a prompt ("F, corde de B"), and plays the note on a real guitar on the beat (mode 1, _locate_), or taps the note name for a given string/fret (mode 2, _identify_). Spaced repetition (FSRS via `ts-fsrs`) decides what comes back; only the first, _cold_ attempt at a card after a delay feeds retention stats. Read `PRODUCT.md` for the product rules and `docs/brief.md` for the original brief. Product docs, plans and UI copy are in French; code, identifiers and comments are in English.

## Architecture

Svelte 5, runes only (forced for all non-`node_modules` files), SvelteKit with `ssr = false`, no component library, native CSS with variables. Layered, ports-and-adapters:

- `src/lib/domain/` — pure logic, no Svelte, no browser APIs. `types.ts` holds the shared domain model (cards keyed by `cardKey(mechanic, itemKey)`, attempts, verdicts, settings, planned items). `exercise/` (the catalog of exercises, `rhythmCatalog.ts`, `Progression`, `Execution`, `startTempo`/`nextTempo`), `time/` (musical time on the target model, see « Musical time » below), `timing/` (the one-answer time relations, until the migration: `beatTiming` for mode 1 with the lead-beat ladder, `identifyTiming` for mode 2, and the `Round` state machine that judges one prompt in time), `mechanics/` (`MechanicIdentity`: id, learner, item key; `MechanicRules` adds a time relation and a judge, `isTimed`/`timedRules`; `locateRules`, `identifyRules`, `rhythmFigureRules`, the `MECHANIC_RULES` registry and `mechanicRules(id)`), `music/` (fretboard, naming, `locateItems`/`practiceCards` over frets 1–11; chords and voicings: `spelling.ts` `SpelledNote`, `chord.ts` degrees and qualities, `voicing.ts` `Voicing` (the degree each string carries) with its stable key and `voicingOccurrences` on the neck, `triads.ts` `closeTriadVoicings`, `candidates.ts` `voicingCandidates`), `scoring/` (verdicts, answer windows, recall threshold, fatigue), `progress/` (FSRS scheduling, temperature cold/hot, `introduction.ts` queue order, `review.ts` cold eligibility, session selectors, stats, neck map, grades), `session/` (the session in segments, see « Exercise sessions »: `trace.ts` `TraceBuilder` and `Segment`, `policy.ts` `next`/`settle`, `block.ts` `diagnoseBlock`, `summary.ts` `summarizeSeries`), `glossary/` (`GLOSSARY`, one definition per term, fr/en, `termOfMeasure`, `termOfFailure`).
- `src/lib/application/` — `ports/` defines the interfaces infrastructure must implement (clock, metronome, note detector (`onNote`, and `onRejected` for attacks whose pitch was not confirmed), cues, calibration, repositories, backup). `app.ts` defines `AppServices`, the single object screens consume, provided through Svelte context (`provideAppServices` / `useAppServices`). `session/contract.ts` defines `PlaySessionController` and its reactive `PlayView` — the contract between orchestration and the play screen. `session/SessionController.svelte.ts` implements it (runes-based state machine: count-in → awaiting → verdict…), asking a `ItemSource` for each prompt; it is built with `(session, prepare, deps)`, where `prepare(sessionId)` returns the selector and the session's executions (one tempo per exercise, frozen at start, `session/executions.ts`). `session/AttemptRecorder.ts` stores attempts (and completes their observations once the span closes), `session/observationSpan.ts` (`ObservationSpan`) collects the observations of one attempt, `session/sensors.ts` turns the detectors and the screen into observation sources (`SensorFactory`, `noteSensor`, `chordSensor`, `attackSensor`, `tapSensor`). `session/plan/` holds the controller of plans (`PlanSessionController`, see « Musical time »); `session/transport.ts` (`Transport`) drives its sounds. Ports added for it: `SoundSchedulerPort`, `TakeBufferPort`, `AttackDetectorPort`, `LevelStateRepositoryPort`. `mechanics/` holds the `MechanicPresenter`s (`locatePresenter`, `identifyPresenter`, `NECK_PRESENTERS`): scene, sensor, prompt, reveal. `services/createAppServices.ts` builds `AppServices` from `SessionDeps`.
- `src/lib/infrastructure/` — adapters. `audio/clock` (one `WebAudioClock` owns the single `AudioContext`; `WebAudioMetronome` schedules beats), `audio/input` (`WebAudioInput`: the one raw input, shared; its frames feed every detector; `TakeBuffer` behind `TakeBufferPort`), `audio/sounds` (`WebAudioSoundScheduler` behind `SoundSchedulerPort`: pitchless filtered-noise timbres per `SoundId`, a journal of the sounds scheduled), `audio/attacks` (`WebAudioAttackDetector` behind `AttackDetectorPort`: pitchless attacks by SuperFlux, `AttackTracker`, `DEFAULT_ATTACK_CONFIG`, `MIN_ATTACK_GAP_MS`; run in the shadow of the note detector while a diagnostic take records, `diagnostics/attackShadow.ts`, `scripts/attack-shadow-report.ts`), `audio/spectral` (FFT and bands shared by detectors), `audio/detection` (AudioWorklet `frame-processor.ts` → onset detection + pitch via `pitchy` → `NoteTracker`), `audio/chords` (`NnlsChordVerifier` behind `ChordVerifierPort`: verifies a played chord against known candidates by fitting harmonic combs, reports at 250/500/1000/2000 ms after each attack, judge variants side by side; real-audio fixtures in `fixtures/`), `audio/cues`, `audio/calibration` (latency measurement), `storage/` (Dexie repositories, backup import/export with validation), `diagnostics/` (the diagnostic journal, see below).
- `src/lib/composition/createApp.ts` — the composition root: wires real adapters into `createAppServices`. Called once in `src/routes/+layout.svelte`.
- `src/lib/ui/` — `primitives/` (the new primitives, plus the Pixel* components and `VerdictSprite` left for `PlayFrame` until plan 3), `shell/` (where the rail shows and which destination is active), `play/` (`PlayScreen`, lane, mode-2 `answer/` keyboard, `PlayFrame` and the `views/` registry), `notation/` (the only VexFlow importer, loaded lazily: `renderFigure(host, figure, options)` → `FigureLayout`, `notationReady()` awaits the embedded Bravura font before engraving), `screens/<name>/` (home, summary, map, calibration, settings). Each screen has a `messages.ts` using `defineMessages({ fr, en })` from `$lib/i18n/index.svelte`; locale comes from stored settings.
- `src/routes/` — thin pages that pull `useAppServices()` and render a screen. `/dev/*` (screens with fake services) and `/diagnostic` are gated by `requireDev()` and 404 in production.

Tests use fakes from `src/lib/testing/fakes.ts` (`FakeClock`, fake metronome/detector/repositories). Repository behavior is specified by reusable contract suites in `src/lib/infrastructure/storage/testing/`, which the Dexie repository specs run.

## Rules that span files

These are fixed product decisions documented in `docs/superpowers/plans/README.md` (read it before changing scoring, timing or audio behavior). All numbers are named constants meant to be tuned, not inlined.

- **Times**: audio scheduling uses `AudioContext` seconds; scoring windows and reaction times are in ms; musical positions and durations are exact fractions of a whole note (`domain/time/`). Onsets are corrected by the calibrated latency of their sensor before judging: `Settings.latency` holds one `SensorLatency` per sensor (`note`, `chord`, `attack`…) with its provenance (`'system'`: measured without the player's gesture; `'player'`: from the player's attacks on the click). The calibration (`audio/calibration/CalibrationService`) measures it without the player: the computer's mic, a second `WebAudioInput` in the same context opened `raw`, is calibrated on clicks heard in silence (`loopLatency`: only clicks heard at one common delay count, with a minimum share and a spread limit), then the interface is compared with it on notes played freely (`pairedDelay`: constant offset found wide, then one-to-one pairs, a minimum of pairs and a spread limit); with the built-in mic alone, the click loop is the latency and a separate bleed check follows, headphones back on; `note` = `chord` = `attack` + the note detector's own delay, anchored on the notes; the reference mic's tracker is more sensitive (`REFERENCE_ATTACK_CONFIG`). It never falls back by itself: a failed reference ends with `reason: 'reference'` and its numbers, and the calibration on the click (`runOnClick`, `player` for all, notes within `PLAY_MAX_OFFSET_MS` of a click) is the player's explicit second choice; the screen shows the measure (`CalibrationMeasure`). `run(deviceId, onProgress)`; the page writes the device, `latency` and `clickBleed` together, only on success. Without an `attack` latency, `PlanSessionController` takes the `note` one, as provenance `player`. `Settings.clickBleed` (click heard on the playing input) makes the rhythm start screen ask for headphones (`PlayView.audioError: 'bleed'`), the first how-to still shown below.
- **Metronome** (the one-answer relations, until the migration; plans use the transport, see « Musical time »): a session's first start waits for `clock.settle()` (a fresh audio output loses its first sounds: `WebAudioClock` waits until it has played `OUTPUT_WARMUP_S`, so the counted bar's downbeat is heard); start at `clock.now() + 0.1` at the earliest; beats already past are dropped. `onBeat` can fire up to 100 ms _before_ the beat — never assume `clock.now() >= beat.time`, compare beat indexes with `>=`, never `===`. Tempo cannot change while running (`setTempo` throws). `at(time, callback)` wakes the session once the audio clock reaches `time`, at the scheduler's next wake-up (never early, at most `DEFAULT_LOOKAHEAD_MS` late), after that wake-up's beats; `stop()` or the returned function cancels it. `FakeMetronome.flush()` interleaves beats and wake-ups in the order they come due.
- **Bar grid** (mode 1): the target always lands on beat 1 of a bar (`alignedPromptBeat` in `domain/timing/grid.ts`); `LEAD_STEPS = [8, 4, 2]` (never 1), so prompts fall on beat 1 or 3. After a target the next prompt waits `RESPIRATION_BARS` (the breathing bar), where a miss shows the right answer (`VerdictView.correction`). The string shows `STRING_PREVIEW_BEATS` before the note (`PlayView.preview`). A lead change between sequences, like a change of scene, is a counted bar (`PlannedItem.countIn`). A `countIn` item may ask `restBars` of silence before its counted bar (the click muted, given back on the beat before the count or on pause); the link asks it at each new chord or set.
- **First note is the answer**; later notes are ignored. The window opens `MIN_RESPONSE_MS` after the prompt: earlier notes belong to the previous prompt and never answer this one. Mode 1 verdicts: wrong pitch/no answer → `wrong`, `|offset| ≤ PERFECT_WINDOW_MS` → `perfect`, else `early`/`late`. Past `LATE_LIMIT_MS` the detector keeps listening for `LATE_CAPTURE_MS`, bounded by the next prompt's string preview (`lateCaptureEnd`): a right note there is `offbeat` (correct, graded Hard, never direct recall — `beatTiming.isDirectRecall` checks it, lengthens the lead), a wrong one stays `wrong`. The attempt is stored once the capture settles. Order: perfect > early/late > offbeat > corrected > wrong (`corrected`: a triad anchor's wrong first chord put right later in the band; `correct: false`, a miss everywhere, only the screen salutes it). This one-answer verdict is `ResponseVerdict`. Every attempt stores `success` (the relation's word on whether the round passed), `correct: boolean | null` (the judge's word on the content; null when nothing was judged, as in a rhythm cycle), `verdict` as an envelope `{ relation, version, value }` (`responseVerdictOf` reads it back for the response relations `RESPONSE_RELATIONS`), `measures`, `aids: Aid[]` and the resolved `plan`. `Attempt.success` is what stats, grades and pacing read, never `correct` (`domain/successBoundary.spec.ts`); for the response relations the recorder computes it with `isResponseSuccess` (correct and not offbeat) until the migration, and `TimingRelation.isDirectRecall` reads it. Mode 2 has no `early` and no `offbeat`.
- **Cold vs hot**: only cold attempts feed retention, FSRS and mastery. A free-play attempt on a learned card untouched for `MIN_COLD_DELAY_MS` is cold too. Deliberate exception: a probe is cold only when passed; a missed probe is stored hot because it measures no forgetting (`probeTemperature`, the only place that decides it).
- **Sessions** are `'learn' | 'free'` for the notes, `'triads' | 'triads-zone'` for the triads (one exercise per session, `createTriadSelector({ mechanic })`; the zone shows on the home screen once `triadZoneOpen`). Free play runs a fixed list (`createListSource`); learn runs `createLearnSelector` (`progress/learnSelector.ts`): retests, cold reviews, resumed notes, new notes from `introductionOrder()`, then consolidation, for `LEARN_SESSION_MS`. A new note is first served as an unaided `'probe'`: a direct recall makes it a review card (`probeCard`), a miss brings the aided presentation on the next prompt. Inside a category the draw is random (injected `random`, `progress/order.ts`): never the previous card, never its mirror (`music/mirror.ts`), another string when possible; a note waits in the queue while its mirror is not acquired. New notes also need `NEW_NOTE_MIN_CARD_SUCCESS` on every note being learned and `NEW_NOTE_MIN_SESSION_SUCCESS` over the last `SUCCESS_WINDOW` mode 1 prompts (`progress/success.ts`); a miss (probes left out) brings a solid card next as hot `'consolidation'` (recovery); hot prompts stay within `MAX_WORKING_SET` cards. Sequences of `SEQUENCE_LENGTH` prompts at one lead and scene are a trial isolated in `progress/sequence.ts` behind `SEQUENCES_ENABLED`. The tempo is per exercise, not a setting (`settings.tempoBpm` is gone, nor is it in the Settings screen): each exercise has a `Progression` (`progressions` store), `startTempo` picks the tempo of an execution (own progression, else the definition's start tempo, else the last tempo on the same mechanic, else `DEFAULT_TEMPO_BPM`), and at the end of a learn session `nextTempo` (`domain/exercise/tempo.ts`) writes the next one, within `[TEMPO_MIN_BPM, TEMPO_MAX_BPM]` (80–160); the tempo never changes during a session (except at a breath of an exercise with levels, see « Exercise sessions »). A tempo may have a generic, optional scope: `Execution.scope`, `Progression.scope`, `PlannedItem.tempoScope`, stored on the attempt as `Attempt.tempoScope`; `startTempo(definition, progressions, scope)` and the end-of-session write work per (exercise, scope), the controller matches a prompt to its execution by both (another scope's tempo restarts the metronome as another exercise's does), and a new scope starts at the definition's start tempo, never at another scope's. Without a scope, everything is as before. The gesture track scopes its grid exercises by grid (a ballad and a blues progress apart); the link has one tempo. Specs: `docs/superpowers/specs/2026-10-02-apprentissage-design.md`, `docs/superpowers/specs/2026-10-03-sondage-avant-apprentissage-design.md`, `docs/superpowers/specs/2026-10-04-rythme-et-consigne-design.md`. One learning procedure (`domain/learning/`, `createLearningProcedure`) is driven by a `LearningSubject` per exercise (`neckSubject`, `triadSubject`) and keeps one `LevelState` per item (lead and aid ladders, moved by `nextLevelState`); the direct-recall threshold is exercise data (`params.recallThresholdMs`, read by `recallThresholdOf`), `ItemSource` names every item source and `choose` picks a series among candidates. The old `createLearnSelector` and triad selector stay until H3 wires the procedure into the controller.
- **Gesture track** (spec `docs/superpowers/specs/2026-10-10-voie-geste-design.md`): session kind `'gesture'` (`createGestureSelector`, `progress/gestureSelector.ts`), one mechanic `chord-grid` (`domain/mechanics/chordGrid.ts`, `learner: 'skill'`: attempts kept with their observations, no card) for four exercises in the order of the ladder, `gesture-link`, `gesture-climb`, `gesture-zone`, `gesture-jam` (`domain/gesture/`: elements, `linkShapes`, `nextZone`, opening from the triad cards acquired, `passageSucceeded` at `PASSAGE_SUCCESS`, `summarizeGesture`). Grids are data written with real symbols (`domain/grid/`: `iohefy-a`, `blues-f`; `parseChordSymbol` over the `SUFFIXES` table, `triadOf` over `TRIAD_OF_QUALITY`, `gridChanges` merges equal symbols in a row); `QUALITIES` holds triads and sevenths, triad code keeps `isTriadQuality`. A passage is a grid played once; each change is an attempt (`ChordGridItem`, key `${element}#${index}`). Rounds of a passage hand over without a gap: `createGridTiming` (`domain/timing/gridChange.ts`) gives each round a `handover` (the next change minus `min(GRID_EARLY_MS, GRID_EARLY_MAX_BEATS` beat`)`); the controller wakes there (`metronome.at`), withdraws the expectations, settles the round (`abandon(now)`), and opens the next change at once (`chained`) unless it has `countIn`, another tempo or another scene. A round with a handover never moves on by `after().advanceAt`; pause, quit and finish cancel the wake-up. In a climb, at a change where no shape of the chord on the set lies strictly beyond the last shape heard, the direction turns there and for the rest of the passage (`climbDirection`, computed by the selector and carried on the items, so the judge stays pure; the aid follows it); passages alternate by their starting direction. Zones span `ZONE_FRETS` frets; an open string counts inside the zone at fret 1 only; the rotation visits every start from 1 to `MAX_VOICING_FRET − ZONE_FRETS + 1`, `ZONE_STEP_FRETS` (5) apart modulo the starts, skipping a zone where a chord of the grid has no shape (`nextZone`, `domain/gesture/passages.ts`). What the implementation decided against the spec is listed in its section « Réalisation ». The home screen offers « Geste » once `AppServices.gesture().open`; the summary sums a gesture session up by exercise and grid (`SessionSummary.gesture`) with « Joué juste » on its misses (`AppServices.contest`).
- **Musical time** (spec `docs/superpowers/specs/2026-10-14-temps-musical-et-sequences-design.md`; its « Réalisation » lists what the code decided against it): a core on the target model, built beside the one-answer relations, which move onto it at the migration (plan H: then `domain/timing/`, `MetronomePort`, `SessionController`'s timing and `isResponseSuccess` go). `RoundPolicy` names its modes (`pairing: { mode, … }`, an object whose settings belong to its mode, e.g. `FirstAnswerSettings`; `verdict`, a registered id such as `'response'` or `'cycle'`; `correction`); `PlanRound` judges any plan by routing through the registered modes (`domain/time/modes/`, `ROUND_MODES`): it computes only the instants no mode decides (`roundTimes`), and a pairing mode owns its timing (`PairingMode.times`, its zones) and checks its own settings (`PairingMode.validate`, called by the engine), with the content judges injected from `domain/judges/` (`contentJudges`, by content kind). The four one-answer relations exist as plans in `domain/exercise/roundPlans.ts`, and `legacyParity.spec.ts` compares them with the old relations until H3. `domain/time/` is pure, no ms outside windows and measures: `Fraction` (exact, normalized, JSON `"3/8"`), `Meter` (`count`, `unit`, `grouping`; nothing assumes 4/4), `TempoMap` (the only conversion between positions and audio seconds; segments carry their unit: ♩ = 100 bpm is `{ bpm: 100, unit: 1/4 }`, always written so in the UI), `Figure` (voices of notes and rests, versioned JSON `figureToJson`/`figureFromJson`, `validateFigure`), `Accompaniment` (a figure of `SoundId`s with an on/off bar mask, `clickAccompaniment`; `renderSounds`/`renderFigure` give `ScheduledSound`s on a map), and `notation/lilypond.ts` (`parseLilyPondRhythm`, a strict LilyPond subset, refuses `#` and `$`; only `domain/exercise/` and `ui/notation/` import it, boundary test). `plan.ts`: what the judge listens for, `RoundPlan` (`prompt`, `Expectation`s with sensor and window `{ ms }` or `{ ofGap }`, `policy.unit` `'response' | 'cycle'`, `handover` where the next round opens without a gap, `mutedBars`), `compileCyclePlan` (a cycle is whole loops of its figure). `judge/align.ts`: `alignAttacks(expectations, attacks, alignContext(plan, map, start))`, a monotone optimal alignment with zones capped at `MATCH_LIMIT`; a lost or added beat is one `shift` (gaining `SHIFT_MIN_MATCHES`; `byS < 0` = beat lost) whose expectations are `dropped`, not missed. `judge/measures.ts`: `CycleReport` (verdict per expectation, extras, measures `fidelity`, `placement`, `precision`, `regularity`, `holdOffset`, `holdDrift` (muted bars only; only the drift may say « accélères »), latency and provenance), `cycleVerdict` (`{ passed } | { reasons }`; placement and precision judge only with a `'system'` latency). `round.ts`: a cycle plan's round judges the whole cycle over its capture window (shifted early by `captureLeadIn` so chained cycles tile time), `RoundOutcome`, `VerdictEnvelope` (relation `'cycle'`), `AIDS`. `levels.ts`: a `Level` is a partial override of the exercise's `LevelParams` (accompaniment, cycle bars, tempo, window, feedback, listen, cursor, cycles per breath, thresholds) with `pass`/`drop` counts; aid levels (`aid: true`) sit below level 1 at negative indexes; `nextLevelState` moves up after `PASS_AFTER_CYCLES` unaided successes in a row and down after `DROP_AFTER_FAILS` failures in a row, never below level 1, failures still counted at the floor; aids the level gives itself (its cursor, `'aid-level'`) do not count as aided (`levelAided`, `session/plan/recordCycle.ts`). State per (exercise, scope, item) in `LevelState` (`levelStates` store). One word everywhere: « niveau » / `level`.
- **Exercise sessions**: kind `'exercise'` plus `SessionRecord.exerciseId` (required on such a session by `validateBackup`; free play of one exercise; today the three rhythm exercises of `rhythmCatalog.ts`, `rhythm-silent-bars`, `rhythm-two-four`, `rhythm-offbeats`, each with `title`, `base` params, `levels`, `figures` and `pick` `'loop' | 'next'`). Home « Rythme » lists them; `/session?kind=exercise&exercise=<id>` (`exerciseFromQuery`) calls `AppServices.startExercise(id)`, which builds a `PlanSessionController` (`application/session/plan/`, deps `PlanSessionDeps`: `sounds`, `levels`, `takes`) beside `SessionController` until the migration; the core outside `plan/` never names `rhythm-figure` (boundary test). The mechanic `rhythm-figure` is an identity only (`learner: 'skill'`, item `${figureId}@${level}`, no relation, judge or presenter): the controller compiles each cycle's plan, judges it with a `PlanRound`, builds the screen model itself (`rhythmStage.ts`, view `rhythm-figure`) and stores a hot `'free'` attempt per played cycle (`recordCycle`: `correct: null`, the round's success, measures and aids, the resolved plan `CyclePlanRecord`). Flow: listen-in `LISTEN_IN_BARS` then a counted bar (both are exercise data: `LevelParams.listenInBars` and `countIn`; `countIn: false`, as in « Métronome sur 2 et 4 », plays right after the listen-in with no count clicks nor countdown; `listenInBars: 0` with `countIn: false` is refused by `resolveLevel`); runs of `cyclesPerBreath` cycles chained without a gap (with silent bars a cycle starts on the first muted bar, so the click's return is judged once, in the silence's cycle); a breath of at least `BREATH_MIN_MS` in whole bars (≥ 2 bars at every level, catalog test) shows the run's marks; a run keeps its level until the breath, where a level change is announced and **the tempo may change** (`Transport.changeTempo`, then listen-in and a counted bar at the new tempo: the one exception to « the tempo never changes during a session »). First encounter (no attempt yet): the `howTo` on the start screen and the figure demonstrated over a lengthened listen-in. `listen()` (key E, L in English) inserts a heard cycle (no round, no attempt; the next played cycle carries `'listen'` when the level's `listen` is `'aid'`); `replay()` (R) plays the last run from `TakeBufferPort` (`keepFrom`/`keepUntil`/`stopKeeping`, `clear` at a new series, `holds`; the input of the whole session, `SESSION_TAKE_MAX_S` = 360) with the click resynthesized from the sound journal, muted bars included. A cycle settles `SETTLE_AFTER_BARS` after it ends; a series lasts `SESSION_MS` (wall time) and ends with its run. **The controller does not decide what comes next** (spec amendment 2026-10-17): the pure policy of `domain/session/policy.ts` does, for any exercise, from data (`next(state, rules, elapsedMs)` → a round, a listen, a breath or the end; `settle` moves the level and runs the anti-blocking; `askListen`). Anti-blocking: `BLOCK_AFTER_FAILS` failures in a row at level 1 → `diagnoseBlock` (`reading`: the same expectation missed or extras on the same spot in `BLOCK_SAME_SPOT_CYCLES` rounds of one item; `execution`: the figure played, the measures fail; `unclear` otherwise) → reading: a listen then a cycle played along (`'play-along'`, an aid), unclear: a listen, execution: the aid level; a block again: one aid level deeper; at the lowest « On change d’air »: the series ends, the measure that breaks is named, `LevelState.resumeAfter` = now + `BLOCK_REST_MS` (the home screen marks it, `AppServices.resting`; it stays playable). The controller keeps a **trace** (`TraceBuilder`: nested segments `session` › `series` › `listen-in`, `count-in`, `run` › `round`/`listen`, `breath`, `pause`; audio-clock seconds; written as bars begin, never when laid out ahead; a cut ends `interrupted`) and the take of each run, and hands both to `SessionMemory` (in memory only, the latest session; the trace is not stored yet, it will be for analysis across sessions). Announcements: `level-up`, `level-down`, `aid-level`, `listen-remedy`, `play-along`, `change-of-air`. The feedback is told in plain words until `PLAIN_WORDS_SESSIONS` sessions of the exercise ended, then by its term and number (`feedbackLine(…, plain)`), the term a `Term` (`ui/primitives/Term.svelte`: dotted on its first occurrence per screen, `provideGlossaryScope`, definition on hover, focus or touch, never during play); a lost or added beat is written above its bar (`shiftMark`). Sounds: the controller talks to sounds only through `Transport` (`session/transport.ts`: one tempo map, `begin` waits `clock.settle()` and rejects with `TransportStopped` if stopped meanwhile, `accompany`, `breath`, `changeTempo` throws over bars already scheduled, `playFigure`, `at`, `countdownAt`), which renders figures onto `SoundSchedulerPort` (`play`, `at`, `cancelAll`, `emitted()`; `cancelAll` empties the journal, so the controller keeps a run's sounds itself). The summary sums an exercise session up in `SessionSummary.exercise` (`summarizeExercise`: level reached, cycles, successes, aided cycles; optional `SessionRecord.levelReached` holds the level at the end of the series), and while the session is in `SessionMemory` its `series` (`summarizeSeries` over the trace: each run with its measures and failed cycles, level changes, listens, share of time played, change of air and what breaks) and the runs still held (`replayable`, `AppServices.replayRun`/`stopReplay`). In development builds only (`development` prop, from `dev`), the judge's full report of the last cycle and « C’était en place » per reason of a failed cycle (`AppServices.contest(attemptId, reason)`, stored as `Attempt.contestReason`). The oracle of the attack sensor is `/diagnostic/oracle` (`infrastructure/diagnostics/oracle.ts`: `ORACLE_TAKES` runs of the journal, the contested first, as WAV and Audacity labels with `suites.json`; then `oracleReport` compares the corrected labels with the sensor, within `ORACLE_MATCH_MS`, and judges the cycles again on them).
- **Play views**: a presenter may give an opaque screen model (`MechanicPresenter.stage`), set by the controller in `PlayView.stage` with the view its exercise names (`ExerciseDefinition.view`, default `DEFAULT_PLAY_VIEW` = `'grid-scroll'`): for the prompt waiting before a counted bar, at the round's opening, and once settled. `ui/play/PlayFrame.svelte` (start, pause on Space, quit, countdown, « Joué juste » on Enter, audio error, fatigue) shows the view from the registry `ui/play/views/index.ts` (`PLAY_VIEWS`); `/session` uses it for `gesture` and `exercise`, notes and triads keep `PlayScreen`. `RhythmFigureView` (pure logic in `views/rhythmFigure.ts`: `cycleMarks(…, beatMs)` with `Mark.line`, exaggerated offsets with `MARK_MIN_OFFSET_PX`, `feedbackLine` telling a failed cycle's reasons in the judge's order, `WORDS_MIN_MS`/`WORDS_MIN_DRIFT_MS_PER_BAR` cutting only passed cycles, `cursorVisible` false in a muted bar) engraves through `ui/notation/`; `/dev/rhythm` shows it and `scripts/functional-ui.mjs` checks it. `GridScrollView` places chords through the pure `views/gridScroll.ts`. The link has its own view, `link-lane` (`LinkLaneView`, pure placement in `views/linkLane.ts`, model `LinkLaneModel`): the notes' lane, a tile per beat, the root or ↗/↘ on the first beat of each bar, the change asked due, the next tour drawn after the last bar; the neck with the notes in circles only when aided. A link tour that fails is played again at once, chained (`ChordGridItem.continued`: no counted bar, its lowest shape not played twice) until one succeeds; a link change is aided from `LINK_AID_AFTER_MISSES` misses in a tour until a tour succeeds (this session only). A relation may give `TimingRelation.targetOffset`: the controller then takes its earliest beat as the target's and counts the bar down to the target (the grid opens a beat before its change, the count still ends on the change). An exercise may carry `howTo` (data, fr/en): before its first prompt in a series the controller stops (`PlayView.briefing`, status paused, `resume` goes on with a counted bar at its tempo); the first one is told on the start screen through `ready()`. `/dev/gesture` plays the link (`?view=grid`: a climb).
- **Mechanics and exercises**: the core (controller, recorder, rounds, sensors) never names `'locate'` or `'identify'` (nor any other mechanic). A mechanic judged by a one-answer relation is a `MechanicRules` (domain) plus a `MechanicPresenter` (application); a mechanic played on plans is a `MechanicIdentity` alone, driven by `PlanSessionController` (see « Exercise sessions »); the neck's two live in the closed `NeckCard` union, allowed only in the neck's own domain (selectors, introduction queue, mirrors, stats, neck map). To add a mechanic: write its rules and add them to `domain/mechanics/index.ts` (`MECHANIC_RULES` and `mechanicRules(id)`, read by backup validation; migrations freeze their own mapping), write its presenter and add it to `SessionDeps.mechanics` (wired in `createApp`), and add a `SensorFactory` to `SessionDeps.sensors` when it needs a new sensor. `application/session/thirdMechanic.spec.ts` plays a fake mechanic end to end to keep that promise. Attempts carry `exerciseId`, `mechanic`, `tempoBpm` and a mechanic-specific `data`.
- **Storage**: Dexie version 8, the target model of the musical-time work (one schema version for all of it): attempts carry `success`, nullable `correct`, the `verdict` envelope, `measures`, `aids` (from the old `aid`) and `plan`; the `levelStates` table holds `LevelState`, keyed `[exerciseId+scope+item]` (empty strings for an absent scope or item; `DexieLevelStateRepository`); settings carry `latency` per sensor and `clickBleed` instead of `calibrationOffsetMs` (which becomes the `player` latency of `note` and `chord`). Upgrades are pure record functions in `storage/migrations/` (`v8.ts`: `attemptToV8`, `settingsToV8`, `backupV3ToV4`), applied alike by the Dexie upgrade and by backup import; they freeze the mechanic → relation mapping of version 7 (`V7_RELATIONS`, a tripwire test against the live registry) and abort the upgrade on an unknown mechanic (the database stays at 7). Only the 7 → 8 step is in `migrations/` so far; older steps stay in `db.ts` and `legacy/` until plan H brings them in. Version 7 added the `scopedProgressions` table, keyed `[exerciseId+scope]`, beside `progressions` for an exercise's own tempo (`DexieProgressionRepository` routes by scope); version 6 added `observations` on attempts and `latencyMs` on sessions; version 5 added `progressions` and reshaped cards and attempts by mechanic and exercise. Backup is version 4; version 3 goes through `backupV3ToV4`, versions 1 and 2 first through the older conversions (`fromV1` in `validateBackup.ts`, `legacy/v2.ts` `fromV2`).
- **Observations**: an attempt keeps every raw observation its sensors perceived during its _span_, from the opening of its round to the opening of the next round (or pause, or end), so it covers the breathing bar and counted bars (`ObservationSpan`, `application/session/observationSpan.ts`). An observation belongs to the span open _on arrival_, not by timestamp; `atMs` is ms since the prompt (round audio time), latency removed, negative when before. Each one records its `fate` (`answer`, an `IgnoreReason`, `other-sensor`, `unreadable`) and the judge's `correct` at play time (null when unreadable or from another sensor). Detector rejections (`NoteDetectorPort.onRejected`: `no-pitch`, `unclear`, `unstable`, `out-of-range`) are stored as `'unreadable'` and are never answers (`Observation.readable`). The attempt is written at the verdict with a snapshot; `AttemptRecorder.completeObservations` rewrites the final list when the span closes (`setObservations`), and `finish()` awaits them. `observations: null` marks attempts from before this existed. The sensor payload is stored as emitted and not validated by storage. `SessionRecord.latencyMs` keeps the calibration offset used. Spec: `docs/superpowers/specs/2026-10-06-journal-observations-design.md`.
- **FSRS** runs without learning steps (`learning_steps: []`): a first Good sends a card to Review. Cards stored at the old 1-beat lead move to 2 (Dexie version 4, and on backup import); attempts keep their recorded lead (`RecordedLeadBeats`).
- **Drawn string** (`ui/play/StringDiagram.svelte`, `STRING_DIAGRAM_AID`): a removable aid (`PlannedItem.stringAid`) on the aided presentation and on the next hot prompt after a miss of that card in the session, gone after `STRING_AID_FADE_SUCCESSES` success; never on reviews or probes. Setting the constant to false removes it; nothing else depends on it. Confusions include `'string-name'`: the open note of the prompted string played instead of the target.
- **Open strings** (fret 0) are never prompted: the prompt names the string by its open note.
- **Chord sensor** (spec `docs/superpowers/specs/2026-10-07-capteur-accords-design.md`): a mechanic gives its sensor an expectation per round (`MechanicPresenter.expectation?` → `ObservationSource.expect?`, opaque to the core); `chordSensor` turns reports into observations. Expectations are withdrawn (`expect(null)`) before a span closes, so a window cut short reports into its own round. The ringing previous chord is never a candidate. The verifier judges each attack from `FIRST_READING_MS` every `JUDGE_EVERY_MS` until a reading is final (expected shape, the same shape `STABLE_READINGS` times, nothing at `NOTHING_FINAL_MS`, or the last one), then stops; a new attack closes an earlier window only once it is older than `ARPEGGIO_SPAN_MS`, so an arpeggio stays whole and a chord played again later is read apart (known risk: a chord played again within that span is read with the first). In the anchor the first chord is the answer: a wrong one shows at once as a provisional miss (`Round.observe` may return `provisional`), and a later right attack in the band settles `corrected` (spec `docs/superpowers/specs/2026-10-09-retours-voie-memoire-design.md`). After a miss, the triad presenters draw what was heard and expected (`MechanicPresenter.feedback`, `VerdictView.heard/expected/gap`) with `ChordShape`, in the style of `Settings.chordDiagram` unless the exercise imposes `ExerciseDefinition.chordDiagram`; a contestable mechanic's miss can be contested in play (« Joué juste », Enter; `PlayView.contest`, `contest()`), until the next prompt. Known risk: D 2-3-2 right after a ringing 7-7-5 is falsely taken for 11-10-10 (frozen fixture).
- **Diagnostic journal** (spec `docs/superpowers/specs/2026-10-07-journal-diagnostic-design.md`): kept apart from learning data, in its own IndexedDB (`neckspert-play-diagnostics`), never in the backup. Only adapters write to it (`DiagnosticSink`: `WebAudioInput`, `DiagnosticAudioRecorder` at 16 kHz, `NnlsChordVerifier` with expectations, full reports and spectra); the core and the mechanics never see it. A take runs from the input's opening to its closing; joins with attempts are made by time at analysis. `Settings.diagnostics` (`enabled: null` = on in dev builds, off in published ones; budget in MB, oldest closed takes pruned). Export: a STORE zip built take by take (`exportArchive.ts`). `ChordReport` carries no spectrum: attempts stay small.
- **Audio input** is opened raw (no echo cancellation / noise suppression / AGC), except the Firefox-on-macOS built-in mic workaround in `WebAudioNoteDetector`. The metronome click is pitchless filtered noise so the detector ignores it; verdict cues are < 150 ms and play after the answer.

## Workflow conventions

- Implementation plans and specs live in `docs/superpowers/plans/` and `docs/superpowers/specs/` (dated, in French). Plan work historically ran in git worktrees under `.worktrees/` on `plan/<id>` branches.
